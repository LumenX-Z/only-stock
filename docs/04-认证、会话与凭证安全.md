## 5. 认证与安全设计

### 5.1 单公司数据存储

系统只服务于一个公司，使用统一数据库文件：

```text
/data/
  inventory.sqlite3
```

存储规则：

1. 数据库统一保存用户、会话、审计和全部库存业务数据。
2. 数据表不设置公司或租户标识，业务 API 不接受公司、租户或数据库路径参数。
3. 每次请求新建数据库会话，请求结束必须关闭；后台任务使用独立会话，禁止复用请求事务。
4. 数据库路径只能来自服务端配置，客户端不能提交或修改。
5. 文件、日志和导出文件名使用安全业务标识，不泄露服务器绝对路径。
6. XLSX 解析不持久化原始文件、工作表内容、文件名、文件哈希、解析状态或错误行。

### 5.2 初始化与用户创建一致性

初始化和用户创建均在同一数据库事务内完成：

1. 仅当数据库中没有任何用户时，应用读取初始化变量并创建首位公司管理员；否则忽略这些变量。
2. 公司管理员创建用户时，在同一事务写入登录账户、密码哈希、角色和显示资料。
3. 任一步失败均整体回滚，不产生可登录的半成品账户。
4. 初始化及用户创建重试必须幂等，不得生成重复账户。

### 5.3 数据归档与销毁

- 本期不提供通过 API 删除数据库文件的能力。
- 数据库文件的归档或销毁属于线下运维操作，必须另行审批和备份，不属于普通管理功能。

### 5.4 登录与会话

- 登录名规范化后不区分大小写，并在全系统唯一。
- 密码使用 Argon2id 哈希，禁止明文、可逆加密或写入日志。
- 密码至少 12 位；初始密码和重置密码首次登录必须修改。
- 会话 ID 使用密码学安全随机数，至少 256 位熵；数据库只保存其哈希。
- Cookie：`HttpOnly`、`SameSite=Lax`、路径为 `/`；按已确认的内网 HTTP 方案**不设置 `Secure`**。
- 会话空闲有效期 8 小时，绝对有效期 24 小时；过期、管理员重置密码、禁用或角色变化时全部失效；本人改密时撤销其他会话并轮换当前会话，当前会话继续有效。
- 浏览器持有的会话 Cookie 已过期、已撤销或在当前数据库中不存在时，任何页面都不得仅凭 Cookie 存在就重定向到工作台；服务端应清除该 Cookie 并回到登录页，避免“登录页 ↔ 工作台”重定向循环。
- 所有登录态写请求必须校验 CSRF Token；JSON API 同样不得豁免。XLSX 文件上传虽是只读解析操作，也使用 `POST` 并校验 CSRF，防止跨站请求滥用解析资源。
- 登录接口按 IP 与登录名限流，失败响应不得泄露账户是否存在。
- 内网 HTTP 不加密传输，仅允许在可信网络使用；文档和部署检查中必须保留此风险提示。

### 5.5 API Key 与 MCP 认证安全

1. 任一启用用户均可通过“我的 API Key”页面或 `/api/v1/api-keys` 管理本人 Key，不能查看、创建或吊销他人 Key；公司管理员也不因此获得他人 Key 的明文。
2. 创建时必须填写 1～50 字符的用途名称。完整 Key 由可识别前缀和至少 256 位密码学安全随机数组成，只在创建成功的响应中显示一次；页面刷新、列表和详情均不得恢复明文。
3. 数据库仅保存完整 Key 的 SHA-256 哈希、用于识别的末四位及元数据；使用固定时间哈希比较。不得记录完整 Key、Authorization 请求头或将其写入审计、异常堆栈和访问日志。
4. 每用户最多 10 把未吊销 Key；达到上限时拒绝创建并提示先吊销。Key 默认长期有效，不自动过期，只允许本人主动吊销；吊销幂等，已吊销 Key 不可恢复。
5. 修改密码、管理员重置密码、角色变化和禁用账户时，在同一用户状态事务内撤销该用户全部有效 Key；`revoked_at` 非空或所属用户非启用时，认证立即失败。
6. `/mcp` 只接受 `Authorization: Bearer <api_key>`，不接受 Cookie 代替认证，也不将会话 Cookie 当作 MCP 身份。Bearer 请求不使用 CSRF；API Key 管理接口仍使用会话认证和 CSRF。
7. 认证通过后，以 Key 当前所属用户和数据库中的当前角色建立本次 MCP 身份，不在 Key 中固化角色或权限。每次 `tools/list` 和 `tools/call` 均重新读取并校验账户、Key 状态和权限。
8. 校验 MCP 客户端的 `Origin`（存在时）及 HTTP `Host`/绑定地址，使用显式允许的本机和服务地址列表，防止 DNS rebinding；不得使用任意 Host 反射生成端点。
9. MCP 请求按 Key ID 与来源 IP 限流，默认每把 Key 每分钟 60 次、每来源 IP 每分钟 120 次，超限返回 429；限制初始化、工具调用及请求体大小，慢连接和流式连接不得耗尽单 worker。
10. 内网 HTTP 会明文传输 Bearer Key，仅允许在可信内网使用；不得经不可信网络、公网代理或不受控客户端传递。Key 泄露时用户必须立即吊销并创建新 Key。

### 5.6 审计

以下事件必须记录操作者、时间、请求 ID、对象、动作及必要的前后状态：系统初始化、用户创建/禁用/重置密码、API Key 创建/吊销、基础资料变更、基础资料停用/启用（含仓库、部门、项目、分类、物资、厂家）、单据提交、软删除、备份和恢复。

通过 MCP 新增基础资料、创建草稿或直接提交新单时，操作者记为 API Key 所属用户，审计的 `source` 为 `MCP` 并记录非敏感 `api_key_id`；普通页面/API 为 `WEB` 或 `API`。MCP 查询不逐条写业务审计；运行日志可记录 Key ID、工具名、请求 ID、耗时和结果代码，不记录完整工具参数或结果。MCP 直接提交与单据及业务审计同事务写入，失败整单回滚。

XLSX 解析只是未保存的填单辅助，不写业务审计；用户随后保存或提交时，只按普通单据记录相应审计，不记录解析来源。单据导出记录单据 ID、单号和导出者。审计不得保存完整上传文件、工作表内容或错误行内容。

禁止记录密码、会话 ID、CSRF Token、完整 API Key、Authorization 请求头或完整数据库内容。审计记录只允许追加，普通业务接口不得修改或删除。
