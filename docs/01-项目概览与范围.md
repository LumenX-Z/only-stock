## 1. 文档目的与范围

### 1.1 建设目标

建设 only-stock，供单一公司使用，实现：

1. 首次启动时创建首位公司管理员，公司管理员可创建和管理其他用户。
2. 公司管理员管理用户、仓库、分类、物资、部门、项目、厂家和全部出入库单，并执行已生效单据软删除、审计查询和手动备份。
3. 库存操作员只执行出入库相关操作，仅可修改或删除本人创建的出入库单，可提交全部普通出入库草稿，但不能管理基础资料或用户。
4. 入库记录厂家，出库不记录厂家；出入库单的每条明细可选关联一个启用项目，同一单据的不同明细可关联不同项目，也可部分留空。
5. 所有出入库单均有仓库和管理部门，库存按仓库与物资计算。
6. 使用单一 SQLite 数据库保存账户、会话、权限和全部库存业务数据，通过统一认证及服务端权限校验控制访问。
7. 使用 Docker Compose 一键部署，并具备备份、恢复、迁移和验收方法。
8. 提供入库、出库 XLSX 模板；解析模板后将有效内容填入新建单页面，由用户核对并手动保存或提交；支持导出单张单据详情。
9. 通过标准 MCP Streamable HTTP 对外提供业务工具；每个启用用户均可创建自己的 API Key，工具清单和每次调用权限均跟随 Key 所属账号。

### 1.2 本期范围

- 账户、会话与权限管理。
- 仓库、部门、项目、厂家、分类、物资管理。
- 入库单、出库单、已生效单据软删除、当前库存查询、有效单据流水、单据查询、审计日志。
- 入库/出库 XLSX 模板下载、无副作用解析、前端快速录入和单张单据详情导出。
- 服务端渲染页面及同版本 JSON API。
- 标准 MCP Streamable HTTP 端点、用户 API Key 全生命周期管理，以及六类资源的查看和新增工具；工具以业务编码 `code` 或单号 `doc_no` 定位记录，输入输出不含内部 ID。
- SQLite 在线备份、保留最近 7 个成功备份集（含手动备份）、离线 CLI 恢复、数据库迁移；第一阶段发布 0.1.0 版本镜像，项目此前尚未正式开发或上线，新增表和字段按首次建库设计，不编写既有数据迁移或兼容逻辑。
- 功能、权限、并发、精度、部署和性能验收。

### 1.3 明确不在本期范围

- 自定义角色、按部门或仓库的数据授权、审批流。
- 批次、序列号、保质期、库位、采购价格、销售成本、财务结算。
- 多计量单位换算、库存盘点、仓库间调拨、项目间调拨。
- 历史时点库存余额查询；系统只提供当前库存余额和有效单据流水，不提供按历史时点重建的库存接口。
- 按项目独立分账的实物库存；项目仅作为明细归属标签和查询筛选条件，不参与库存余额计算。
- 负库存、已生效单据直接编辑。
- HTTPS、反向代理、公网部署、多副本高可用。
- 根据入库厂家追踪某次出库的具体实物来源；本系统不建立批次对应关系。
- 通过 XLSX 上传直接创建或修改单据、导入批次及错误行持久化、逐行 XLSX 错误报告、导入结果查询、异步导入队列。
- 一个文件生成多张单据、在已有草稿编辑页解析 XLSX、按筛选条件批量导出多单清单，以及通过 XLSX 未经用户操作直接提交并改变库存；MCP `document_create` 的显式直接提交不属于 XLSX 导入。
- MCP 项目管理工具、库存独立查询工具、用户/审计/备份工具，以及 MCP 修改、删除、软删除、停用、启用和单独提交已有草稿工具。
- MCP Resources、Prompts、旧版 HTTP+SSE 传输、独立 MCP 服务进程和公网 MCP 接入。

如后续增加上述能力，必须重新评审数据模型、库存视图和权限矩阵。

### 1.4 关键术语

| 术语         | 定义                                                                                                      |
| ------------ | --------------------------------------------------------------------------------------------------------- |
| 数据库       | 系统唯一的 SQLite 数据库，保存账户、会话、权限、审计和全部库存业务数据                                    |
| 物资         | 可管理库存的最小物资对象，具有唯一物资编码、所属一级或二级分类、计量单位和数量类型                        |
| 有效单据     | 状态为 `POSTED` 且未软删除的入库单或出库单；草稿和已软删除单据不计入库存                                |
| 软删除       | 对已生效出入库单保留单据及明细记录，但不再计入库存汇总；已生效单据不可修改                                |
| 明细项目     | 出入库单每条明细可选关联的一个启用项目；同一单据内各行可不同、可为空；仅用于归属、筛选和统计，不参与库存分账 |
| 千分比整数   | 实际数量乘 1000 后保存为 SQLite `INTEGER`，如 `1.25` 保存为 `1250`                                  |
| 快速录入     | 在新建入库或出库页面解析 XLSX，将有效单据头和明细填入当前表单；不创建草稿、不保存解析结果、不改变库存     |
| 部分填入     | 文件级校验通过但部分明细存在错误；仅将有效行填入页面并显示错误摘要，由用户核对后决定是否保存或提交        |
| MCP          | Model Context Protocol；本系统通过标准 Streamable HTTP 提供工具，使用 API Key 认证，不使用浏览器会话认证  |
| API Key      | 用户自助创建的 MCP 访问凭证；完整明文仅在创建时显示一次，数据库只保存哈希，权限始终跟随所属账号           |
| MCP 直接提交 | `document_create` 以 `submit=true` 调用时，在一个写事务内创建并提交出入库单；失败整单回滚，不保留草稿 |

## 2. 已确定的总体设计

| 决策项         | 最终方案                                                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 全栈技术       | FastAPI、Jinja2、HTMX、少量原生 JavaScript、SQLAlchemy 2、Alembic、pytest、Ruff（仅开发校验）                                      |
| 前端形态       | 服务端渲染，不建立独立 SPA                                                                                                       |
| 使用范围与存储 | 仅供单一公司使用；一个 SQLite 数据库保存账户、会话和全部业务数据                                                                 |
| 认证           | 统一账户；浏览器/JSON API 使用服务端会话，MCP 使用用户 API Key；登录名全系统唯一                                                 |
| 角色           | 公司管理员、库存操作员两种固定角色                                                                                               |
| 数据范围       | 两种角色均可查询全部业务数据，不按部门或仓库限权                                                                                 |
| 基础资料管理   | 仅公司管理员可创建、按规则删除、停用或启用仓库、部门、项目、分类、物资和厂家；创建后不可修改                                     |
| 编码规则       | 六类基础资料的实体编码字段统一为 `code`，由服务端在创建事务内自动生成；用户不输入、不修改，停用或删除后不回收复用                |
| 名称唯一       | 仓库、部门、项目、厂家名称在各自表内唯一（去首尾空白后精确比较，停用记录仍占名）；分类与物资名称按[《数据模型与实体约束》6.4](05-数据模型与实体约束.md#64-分类与物资)的层级范围唯一            |
| 分类停用       | 分类存在任一未停用的子分类或物资（一级分类含全部后代分类及后代物资）时禁止停用，须自底向上手工停用；不级联停用                   |
| 停用可恢复     | 仓库、部门、项目、分类、物资、厂家停用后均可启用；启用只改状态并写审计，不改历史单据与库存；启用下级资料要求其上级分类已启用     |
| 普通出入库     | 操作员仅可修改、删除本人创建的出入库单，管理员可操作全部出入库单；两种角色均可提交全部普通出入库草稿                             |
| 项目           | 每条明细可选关联一个启用项目，同单可混用、可为空；同一物资可按项目拆行；不作为库存分账维度                                                   |
| 厂家           | 入库明细行必填，出库明细不填写                                                                                                   |
| 部门与仓库     | 均在单据头必填，每单一个部门、一个仓库                                                                                           |
| 库存余额       | 不维护余额表，通过有效单据明细视图实时汇总                                                                                       |
| 单据生效       | 草稿提交后立即生效，无人工审核                                                                                                   |
| 纠错           | 已生效出入库单可软删除；已生效单据不可编辑，操作员仅可软删除本人创建的单据，管理员可软删除全部单据                               |
| 负库存         | 完全禁止；任何提交或软删除均不得使任一物资余额小于零                                                                             |
| 数量           | 整数或最多三位小数；数据库使用千分比整数，不使用浮点累计；单一仓库物资余额不得超过 `MAX_BALANCE_MILLI = 9_000_000_000_000_000_000` |
| 并发           | 写操作使用 `BEGIN IMMEDIATE` 串行，事务内重新计算库存                                                                            |
| 部署           | 单个 `app` 服务，直接暴露 HTTP 端口，无 HTTPS、无反向代理                                                                        |
| 备份           | 每日 SQLite 在线备份，保留最近 7 个成功备份集（含手动备份）；公司管理员可手动备份，恢复仅通过离线 CLI                            |
| 单据模板       | 入库、出库分别提供 XLSX；使用业务名称而非编码，物资增加一级、二级分类列                                                          |
| 快速录入       | 仅在新建页使用；一个文件对应一张单据，文件最大 5 MiB、最多 2,000 非空数据行；解析不创建或修改任何业务数据                        |
| 解析容错       | 文件级错误整份拒绝且保留原表单；行级错误跳过，有效行填入页面；只显示当前页错误摘要，不生成错误报告                               |
| 填单行为       | 非空表单须确认整体替换；解析成功才替换单据头和全部明细，不追加；解析失败不改变当前表单                                           |
| 保存与提交     | 用户手工点击；保存调用普通创建草稿接口，提交依次调用创建草稿和提交接口；创建继续使用客户端 `request_id` 幂等                        |
| 单据导出       | 单张单据导出 XLSX；草稿按当前资料，历史单按快照；导出文件再次解析时仍按当前资料校验                                              |
| MCP 传输       | 官方 MCP Python SDK，标准 Streamable HTTP，单一 `/mcp` 端点；与 FastAPI 同应用、同端口、单进程                                   |
| API Key        | 用户自助创建和吊销；明文仅创建时显示一次，仅存哈希；每用户最多 10 把有效 Key；改密、角色变化和禁用全部撤销                       |
| MCP 工具       | 六类资源各 `list/create`，另提供 `inventory_list` 实时库存查询，共 13 个；操作员可见 8 个，管理员可见 13 个；每次 `tools/list` 和 `tools/call` 实时按账号权限过滤/校验 |
| MCP 引用       | 基础资料用 `code`、单据用 `doc_no` 定位；关联用 `<resource>_code`；单条定位不使用名称或内部 UUID、`id`、`*_id`                   |
| MCP 单据       | `submit=false` 创建草稿；`submit=true` 创建与提交整体原子，失败不留草稿；工具不接收 `request_id`，由服务端生成                     |
| MCP 去重       | 服务端按创建者 + 规范化指纹在 300 秒窗口内对 MCP 建单去重；命中返回原单并标 `deduplicated=true`，窗口外允许重复建单              |
| MCP 安全       | Bearer 与 Cookie/CSRF 分离；Origin/绑定地址校验，按 Key/IP 限流；写操作审计标记 MCP 来源，日志不记完整凭证                       |
